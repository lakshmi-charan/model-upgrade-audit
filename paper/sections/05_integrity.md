# A silent environment failure and what it would have shown {#sec:integrity}

Repeat-aware evaluation assumes that differences between runs come from the model. Our own study shows how easily that assumption fails. During the confirmatory collection, the clinical record server stopped accepting connections partway through the clinical run and stayed down for roughly ten hours (2026-10-07, about 16:00 UTC, to 2026-10-08, about 01:30 UTC). The environment check at the start of the job had passed, and the harness recorded every tool response verbatim, including `connection refused`. It then graded each episode as usual. Agents that met the error usually reported that the server was unreachable and stopped. The grader scored this as a failure on most tasks but as a success on conditional tasks whose correct action is to order nothing.

We found the problem only when reading the individual episodes behind the one cell with a significant reliable-negative-flip count in our first analysis (Table [-@tbl:contam]): the provider's official replacement model had "reliably" failed to record a blood-pressure reading on five tasks, and on the first one we opened the server had refused the connection in two of the three runs. A pattern scan of every graded tool response (connection refused, failed new connection, exhausted retries, read time-outs, aborted connections) then found **2,077 of 3,300 clinical episodes (63%)** affected. The share ranged from none for one model, which ran before the outage, through 28% and 42% for the two newer OpenAI models and 48% and 69% for the two Gemini models, to 84–86% of all episodes for the six open-weight models, which ran almost entirely during it. The operations and MLOps testbeds and the clinical pilot contained no such errors.

Our frozen protocol already stated that episodes lost to infrastructure errors are not recorded but re-run. The harness enforced this for errors raised by the model API, but not for errors the environment returned to the agent as ordinary tool output. We quarantined the affected episodes, changed the harness to check the server before every episode and to refuse any episode whose trace contains a connection error, and re-ran them with the same prompts, decoding settings and response cache. All confirmatory results in this paper are computed on the repaired data; the analysis of the contaminated data is kept as an audit record.

**What the contaminated data would have told us.** Table [-@tbl:contam] and Figure [-@fig:integrity] compare the clinical results computed on the contaminated data, which is what we would have published had we trusted the job-level check, with the results on the repaired data. Three apparent losses became gains. Gemma 3 → Gemma 4 went from a significant *loss* of 11 points to a significant gain of 13; Qwen3 → Qwen3.5 went from −3 to +11, and GPT-5 nano → GPT-5.6 Luna from −6 to +3. In the other direction, the Mistral step's significant gain of 6 points vanished (−0.3). The only cell with a significant reliable-negative-flip count in the contaminated analysis (five "reliable" breaks for the provider's official replacement model, Holm-corrected p = 0.006) vanished; on clean data that cell has none. The drop in pass^3 that motivated hypothesis H6 (Gemma 0.58 → 0.35) became a rise (0.51 → 0.72).

The outage did not simply lower everyone's scores. Most of the affected episodes were still graded, and **43% of them (896 of 2,077) were graded as successes even though the agent could not read the record**. On the two conditional ordering templates (replace magnesium or potassium if the last value is low), 64–65% of blind episodes passed, because doing nothing is the correct action whenever the stored value is normal. Models also differed in how they behaved when blind. One older model submitted orders in 79 of its 252 affected episodes while the record server was refusing its connections; no other model did so in more than 9.2% of its affected episodes. So the outage turned differences in behaviour *under failure* into apparent differences in capability, which is why it reversed upgrade effects instead of merely adding noise.

**Lesson.** An agent evaluation that grades the final state cannot tell a model failure from an environment failure unless it checks the environment *per episode*, not per job. Run-to-run variation, the very signal a repeat-aware audit uses, is also what a partial outage produces. We release the scan script and recommend that agent benchmarks report, alongside success rates, the number of episodes rejected for environment errors.

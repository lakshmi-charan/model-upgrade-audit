# Introduction {#sec:intro}

Teams that run AI agents in production change the underlying model on a schedule they do not control. Providers retire models within months of release, and the recommended replacement is usually a newer member of the same family that scores higher on public benchmarks. The engineering question at that moment is narrow and practical: *which of the workflows that work today will stop working after the switch?* A higher average score does not answer it. An upgrade can raise mean success while breaking a particular workflow, a pattern known from classifier updates as negative flips [@yan2021pct; @xie2021regression] and recently documented for single-turn LLM benchmarks [@cacioli2026beyond; @sheng2026nouniversal].

For agents the question is harder for two reasons. First, agents are noisy. The same model on the same task can succeed in one run and fail in the next, even at temperature zero, and run-to-run variation in agent benchmarks can be as large as the gap between model versions [@arino2026identical; @yagubyan2026consistent]. A regression suite that runs each task once will report "regressions" that are only noise. Second, an agent's failures are actions with side effects, taken in an environment that can itself fail. A regressed agent may place an order nobody asked for; an agent facing a broken environment fails for reasons that have nothing to do with the model.

We ask what actually changes when an agent's model is upgraded to the next version of the same family, and answer with a pre-registered, repeat-aware audit. Six upgrade pairs from four families, including a provider's two official retirement replacements, run every task three times on three executable testbeds whose grading reads only the resulting state: a clinical agent that reads and writes a FHIR health record (MedAgentBench tasks [@jiang2025medagentbench] plus hazard variants), an operations agent acting on real services (PostgreSQL, Gitea, Mailpit, Redis, an S3 store and a ledger database), and an MLOps agent that diagnoses production model degradation by re-executing pipeline components. A within-task permutation test separates *reliable* negative flips (old model passes all runs, new model fails all runs) from flips that same-model repetition produces by chance.

Our findings, and contributions, are:

1. **One-shot regression reports are at least half noise.** Of the tasks a single run flags as regressed, 63% (95% CI 50–76%) pass again on re-run. Re-running each failure up to twice before flagging it removes these false alarms for about a fifth more episodes, and a first-action probing heuristic we designed does not beat this simple rule.
2. **Reliable regressions are rare and, at this scale, not separable from churn.** Across 18 pair–testbed cells, fewer than one in twenty tasks that the old model always solved is always failed by the new one, and no cell's count of reliable negative flips survives correction for multiple testing. Same-family upgrades in our sample are better on average and, as far as three runs can tell, not broken in places.
3. **Newer generations take fewer unlicensed actions.** Writes outside the licensed set fall significantly in five of six pairs and rise significantly in none, contrary to the mixed picture our pilot suggested.
4. **A silent environment failure can manufacture every effect we looked for.** A ten-hour outage of the clinical server during our own collection corrupted 63% of clinical episodes, and 43% of those were still graded as successes, mostly because doing nothing is correct on many conditional tasks. On that data, three upgrades appeared to *lower* success, the provider's official replacement appeared to *reliably break* a vital-sign workflow, and reliability appeared to erode; all three disappeared on clean data. We describe how the failure evaded a per-job health check and release the per-episode check and scan that caught it.

All hypotheses, task sets and analysis code were frozen before the confirmatory runs; we report every pre-registered test, including the five of six (one added by amendment) whose criteria were not met, and list every amendment and deviation (Appendix [-@sec:protocol]). Every episode, the serving provider of every call and the analysis code are released.
